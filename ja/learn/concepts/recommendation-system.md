# レコメンドシステムとは？

**レコメンドシステム**（レコメンダーシステム、推薦システム）とは、特定の
ユーザーが次に欲しがりそうなアイテムを予測し、その候補を短いランキング形式で
提示するソフトウェアです。何千・何百万件ものカタログを人が自分で検索する
代わりに、その人の好みや状況に合う少数のアイテムをシステムが浮かび上がらせ
ます。「この商品を買った人はこれも…」、トップページのパーソナライズ枠、
「あなたへのおすすめ」フィード、ページ下部の「関連記事」— これらはすべて
レコメンドシステムが働いている例です。

形式的には、レコメンダーは **インタラクション**（誰が何に反応したか）の履歴
から学習し、スコアリング関数を作ります。あるユーザーが与えられると、候補
アイテムをすべてスコア付けし、上位 *K* 件を返します。この分野の本質は、手元に
あるデータからそのスコアリング関数をうまく学習することと、ページ読み込みの
最中にリクエストへ応答できるほど高速に配信することにあります。

## レコメンドシステムが使われる場所

レコメンダーは、カタログが人の閲覧しきれる範囲を超えるあらゆる場所に登場します。

- **EC** — 商品レコメンド、クロスセル・アップセル、「よく一緒に買われる商品」。
  [購買ログからレコメンド](/ja/learn/use-cases/purchase-logs) を参照してください。
- **メディア・ストリーミング** — 次に見る動画、聴く曲、読む記事。
- **ニュース・コンテンツ** — 関連記事モジュールやパーソナライズされたフィード。
- **マーケットプレイス・分類広告** — 閲覧行動に合わせた出品のマッチング。
- **B2B・SaaS** — ユーザーが必要としそうなテンプレート、連携、ドキュメントの提案。

共通するのは **ロングテール** です。放っておけば一握りの人気アイテムが注目を
独占しますが、優れたレコメンダーはカタログの残り部分がそれぞれの読者・購入者に
出会うための仕組みなのです。

## レコメンダーの種類

大きく分けて 3 つの系統があり、どのシグナルから学習するかで区別されます。

### コンテンツベースフィルタリング

コンテンツベースの手法は、ユーザーがすでに気に入ったアイテムに **似ている**
アイテムを推薦します。ここでの類似度は、映画のジャンル、商品のカテゴリ、記事の
テキストといったアイテムの属性から測ります。「kubernetes」タグの記事をいくつも
読んでいれば、コンテンツベースのシステムはさらに「kubernetes」の記事を推薦
します。豊富なアイテム特徴量を必要とし、新規アイテムにも対応できますが、
ユーザーがすでに見たものの狭い枠の中に閉じ込めがちです。

### 協調フィルタリング

協調フィルタリング（CF）はアイテムの属性を無視し、**多数のユーザーにまたがる
インタラクションのパターン**だけから学習します。「あなたと似た振る舞いをした
人たちは、こういうアイテムにも反応した」というわけです。明示的なタグではなく
集団の知恵を活用するため、カテゴリを横断した意外性のある推薦を生み出せます。
CF は現代のレコメンダーの主役であり、Recotem が土台とするアプローチでもあります。
[協調フィルタリングとは](/ja/learn/concepts/collaborative-filtering) を参照して
ください。

### ハイブリッド

ハイブリッドは両者を組み合わせます。たとえば履歴のあるユーザーには協調
フィルタリングを使い、履歴がまだない **コールドスタート**（新規ユーザーや
新規アイテム）にはコンテンツベースや人気度ベースの推薦にフォールバックします。
大規模な本番システムは、実運用ではほぼ常にハイブリッドです。

::: tip Recotem の立ち位置
Recotem のアルゴリズムは協調フィルタリングのモデルです。アイテムのテキストや
画像ではなく、インタラクション行列（誰が何に触れたか）から学習します。タイトル
やカテゴリといったアイテムメタデータは *レスポンスを充実させる*（API が読みやすい
フィールドを返す）ために付与できますが、モデルには入力されません。アイテムの
内容そのものを推論に使う必要がある場合、それはコンテンツベースまたはハイブリッド
の課題であり、Recotem の中核の対象外です。
:::

## 明示的シグナルと暗黙的シグナル

すべてのレコメンダーは **フィードバック** から学習し、フィードバックには 2 つの
形があります。

- **明示的フィードバック** は意図的な評価です。5 段階のレビュー、高評価・低評価、
  「いいね」など。正確ですが希少で、そもそも大半のユーザーは何も評価せず、存在
  する評価も両極端に偏りがちです。
- **暗黙的フィードバック** は行動の痕跡です。クリック、閲覧、購入、再生、滞在
  時間など。豊富で常時発生しますが、ノイズが多いのが特徴です。クリックは確実な
  支持とは限らず、クリックが *ない* ことも明確な「ノー」ではありません。

実務では、暗黙的フィードバックが主流です。通常の利用の副産物として得られる
から — 購入もページ閲覧もすでにログに残っているからです。このトレードオフは、
どのアルゴリズムを選ぶか、どう評価するかの両方を左右します。Recotem は暗黙的な
インタラクションデータ（各行は単に「このユーザーがこのアイテムに触れた」）を
前提に設計されており、推奨アルゴリズム（IALS、RP3beta）が暗黙的フィードバックの
モデルであるのはそのためです。詳しくは
[暗黙的フィードバックと明示的フィードバック](/ja/learn/concepts/implicit-explicit-feedback)
を参照してください。

## オフラインからオンラインへのパイプライン

ほぼすべての本番レコメンダーは 2 つのフェーズに分かれます。

**オフライン（学習）:**

1. **インタラクションを収集** し、`(ユーザー, アイテム[, 時刻])` の行の表にする。
2. データを **クレンジング** する — null の ID を除去し、重複ペアを排除し、最小
   サイズを担保する。
3. 品質を正直に測れるよう、学習用と検証用（ホールドアウト）に **分割** する。
4. 1 つ以上のアルゴリズムを **学習・チューニング** し、ハイパーパラメータを探索
   する。
5. nDCG@K や Recall@K などのランキング指標で各候補をホールドアウトセットで
   **評価** し、最良のモデルを残す。
   [推薦システムの評価指標](/ja/learn/concepts/evaluation-metrics) を参照して
   ください。
6. 勝ち残ったモデルをデプロイ可能なファイルとして **書き出す**。

**オンライン（配信）:**

7. 学習済みモデルを API の背後に **ロード** する。
8. `user_id` を受け取り、上位 *K* 件を返す形でリアルタイムに **応答** する。

オフラインのフェーズは重く、周期的に実行します（新しいデータが届くたびに毎晩・
毎週など再実行）。オンラインのフェーズは軽く、常時稼働します。両者を分離すると、
稼働中の API を止めることなく、大きなマシンで再学習できます。

## Recotem による各ステージの実装

Recotem はこのパイプラインを 3 つのコマンドと 1 つのファイルに落とし込みます。
単一の YAML **レシピ** が信頼できる唯一の情報源です。1 つのレシピが 1 つの
モデルと 1 つの `/v1/recipes/{name}:recommend` エンドポイントを定義します。
`recotem train` がオフラインのフェーズを実行して署名済みアーティファクトを
書き出し、`recotem serve` がそのアーティファクトを読み込んでオンラインのフェーズ
を実行します。両者はアーティファクトファイルだけを介して通信するため、別々の
マシンで動かせます。

パイプライン全体をカバーする、最小限で実在の構文のレシピを示します。

```yaml
name: news_articles

source:
  type: csv
  path: ./data/interactions.csv
  dtype:
    user_id: str
    item_id: str

schema:
  user_column: user_id
  item_column: item_id
  time_column: ts

cleansing:
  drop_null_ids: true
  dedup: keep_last

training:
  algorithms: [IALS, RP3beta, TopPop]
  metric: ndcg
  cutoff: 20
  n_trials: 40
  split:
    scheme: time_user
    heldout_ratio: 0.1
    seed: 42

output:
  path: ./artifacts/news_articles.recotem
  versioning: append_sha
```

各ブロックがパイプラインの 1 ステージに対応します。

- **`source`** — インタラクションの取得元（`csv`、`parquet`、`bigquery`、
  `sql`）。これが *収集* です。
- **`schema`** — どのカラムがユーザー、アイテム、時刻かを指定します。
- **`cleansing`** — null 除去、重複排除、最小サイズのゲート。これが
  *クレンジング* です。
- **`training`** — 候補となる `algorithms`、最適化するオフライン指標 `metric` と
  `cutoff`、Optuna の試行回数（`n_trials`）、そして `split` の方式。*分割・学習・
  チューニング・評価* が 1 つのブロックにまとまっています。`IALS`、`RP3beta`、
  `TopPop` は Recotem の組み込みアルゴリズムの一部です（全体には `CosineKNN`、
  `DenseSLIM`、`TruncatedSVD`、`BPRFM` も含まれます）。
- **`output`** — 勝ち残ったモデルを署名済みアーティファクトとして書き出す先。
  これが *書き出し* です。

オフラインのフェーズを実行します。

```bash
recotem train recipes/news_articles.yaml
```

Recotem はデータを取得してクレンジングし、ホールドアウト分割上の nDCG@20 で
採点しながら 3 つのアルゴリズムにわたる Optuna 探索を実行し、最良のモデルを
署名済みバイナリアーティファクトとして `./artifacts/` に書き出します。続いて
オンラインのフェーズを開始します。

```bash
recotem serve --recipes ./recipes/
```

サーバーはアーティファクトを HMAC 検証してロードし、レコメンドエンドポイントを
公開します。あるユーザーの上位アイテムを尋ねてみます。

```bash
curl -s -X POST http://localhost:8080/v1/recipes/news_articles:recommend \
  -H "X-API-Key: <plaintext>" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "u1", "limit": 10}' | jq .
```

```json
{
  "request_id": "a1b2c3d4e5f6",
  "recipe": "news_articles",
  "model_version": "sha256:a3f2...e91d",
  "items": [
    {"item_id": "item-42", "score": 0.91},
    {"item_id": "item-17", "score": 0.84}
  ]
}
```

これで完全なレコメンドシステムです。インタラクションを入力すると、ランク付け
された一覧が HTTP 経由で返ってきます。[Serving API](/ja/docs/serving-api) は、
アイテム間の「関連アイテム」クエリ向けの `:recommend-related` や、多数の
ユーザーを一度に採点するバッチ動詞も提供します。

::: warning 新規ユーザーは 404 を返す
学習時に登場しなかった `user_id` は `404 UNKNOWN_USER` を返します。これは想定
された挙動で、コールドスタートのケースです。アプリケーション側で、人気アイテムに
フォールバックするか、ユーザーが現在見ているものをシードにした
`:recommend-related` クエリで対処してください。
:::
