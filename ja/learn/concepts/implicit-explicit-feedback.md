# 暗黙的・明示的フィードバックとは

どのレコメンダーも、人々がアイテムとどう関わったかの記録から学習します。その
記録には 2 種類あります。ユーザーがどれだけ好きかを意図的に表明する **明示的
フィードバック**と、ふだんの行動から好みを *推定* する **暗黙的フィードバック**
です。この区別は理屈っぽく聞こえますが、実務上のほぼすべての判断 — どのデータを
集めるか、どのアルゴリズムを学習させるか、どの評価指標が真実を語るか — を左右し
ます。このページでは両者を説明し、なぜ実システムでは暗黙的フィードバックが主流に
なるのか、そして Recotem がそれをどうモデル化するのかを解説します。

この分野が初めてなら、まず柱となる
[レコメンドシステムとは](/ja/learn/concepts/recommendation-system) の概観から
始め、フィードバックの区別についてはこのページに戻ってきてください。

## 2 種類のシグナル

**明示的フィードバック**は、ユーザーが尺度上で意識的に与える好みです。

- 5 段階の星評価（映画、商品、レストラン）
- 高評価 / 低評価（サムズアップ・ダウン）
- レビューの数値スコア
- 「興味なし」/「この種類を減らす」

決定的な特徴は「意図」です。ユーザーは自分の意見を、たいていは順序のある尺度で
*あなたに伝えており*、低い評価は正真正銘の負のシグナルになります。

**暗黙的フィードバック**は、ユーザーが評価のつもりで行ったのではない行動から
*推定* される好みです。

- クリックやページ閲覧
- 購入やカート追加
- 楽曲・動画の再生、視聴時間、滞在時間
- 検索、ブックマーク、フォロー

ここでのシグナルは間接的です。購入は強い興味を示唆し、クリックはより弱く、3 秒の
動画視聴はさらに弱いシグナルです。そして重要なのは、暗黙的データはほぼ常に
**正例のみ**だということです。ユーザーが *何をしたか* は分かっても、「これは
嫌い」という明示的な情報は得られません。

| | 明示的 | 暗黙的 |
|---|---|---|
| 例 | 星 4 つの評価 | 購入、クリック、再生 |
| ユーザーの意図 | 意識的な意見 | 行動の痕跡 |
| 尺度 | 順序あり（1〜5、±1） | 有無 / 回数 |
| 負のシグナル | あり（星 1 つは本物） | なし（「ない」は曖昧） |
| 量 | 少ない | 豊富 |
| ノイズ | 1 件あたり小さい | 1 件あたり大きい |

## なぜ実務では暗黙的フィードバックが主流なのか

教科書はしばしば MovieLens の星評価データセットから話を始めるため、明示的評価が
標準だという印象を与えがちです。ところが本番システムでは逆で、多くのチームが実際に
持ち、使っているのは暗黙的フィードバックです。理由はいくつかあります。

- **量**。セッションごとにクリック・閲覧・再生が発生します。何かを評価する
  ユーザーはごく一部にすぎません。暗黙的ログはしばしば桁違いに大きくなります。
- **常時取得でき、コストがかからない**。暗黙的シグナルは通常利用の副産物として
  自動的に集まります。専用 UI を作る必要も、ユーザーの手間も、無視されがちな
  プロンプトもありません。
- **カバレッジ**。評価は疎で、わざわざ評価する自己選択的な少数派 — しかも異常に
  良い/悪い体験の後に評価しがち — に偏ります。暗黙的データは、トラフィックのあった
  ほぼすべてのユーザーとアイテムを覆います。
- **鮮度**。行動は「いま」ユーザーが何を求めているかを反映します。2 年前に残された
  評価は古びているかもしれません。

トレードオフは、暗黙的フィードバックがよりノイジーで、かつ一クラス（正例のみ）で
あることです。クリックは誤タップかもしれず、購入は贈り物かもしれません。そして
ユーザーがある映画を *一度も観ていない* という事実は、ほとんど何も語りません —
嫌ったのかもしれないし、単に目に触れなかっただけかもしれません。この曖昧さの扱いが、
暗黙的フィードバック推薦の中心的な技術課題です。

## 正例のみ問題: 信頼度とネガティブサンプリング

明示的評価があれば、推薦を *評価予測* として定式化できます。ユーザーが与えた評価を
もとに、未見アイテムに付けるであろう評価を予測し、取り置いた評価との誤差を最小化
します。暗黙的データにはそのような教師信号がありません — 回帰の対象となる負例の
ラベルが存在しないのです。正例のみの行動を学習可能な目的関数へと変える手法は、
大きく 2 系統あります。

**信頼度による重み付け**。古典的な手法（Hu, Koren & Volinsky, 2008。implicit ALS
の背後にあるモデル）は、*すべての* ユーザー×アイテムの組を訓練例として扱います。
観測された相互作用は正例、観測されなかった膨大な組は負例として扱いますが、それぞれ
どれだけ確信できるかを表す **信頼度** で重み付けします。何度も相互作用したアイテムは
高い正の信頼度を得て、未観測アイテムの広大な海は低いながらもゼロではない負の信頼度を
得ます。何もサンプリングで捨てず、行列全体が寄与し、「本当に嫌われている」と「単に
まだ見ていない」の区別は重みが担います。

**ネガティブサンプリング**。もう一方の手法（BPR: Bayesian Personalized Ranking で
用いられる）は、タスクを *ペアワイズなランキング* として捉え直します。観測された
正例アイテムごとに、未観測アイテムを 1 つ負例として無作為に引き、正例が負例より
上位にランクされるようモデルを学習します。未観測空間の全体を重み付けする代わりに、
1 ステップあたり扱いやすい数の負例を *サンプリング* します。これはスケールしやすく、
ランキング順を直接最適化します。

両者は同じ直感を共有しています。**相互作用は興味の証拠であり、相互作用がないことは
弱く不確かな反証にすぎない** — 決定的な「嫌い」ではない、という直感です。2 系統は
計算資源の使い方が違うだけで、一方はすべての負例を重み付けし、もう一方は少数を
サンプリングします。

## アルゴリズムと評価指標の選択への影響

手元にあるフィードバックの種類は、2 つの決定を左右します。

**アルゴリズム**。1〜5 の尺度上での誤差最小化を狙って設計された評価予測アルゴリズムは、
クリックしかない状況には向きません。必要なのは、一クラス・正例のみのデータ向けに
作られたモデル — 信頼度重み付きの行列分解、アイテム間類似度、グラフ / ランダム
ウォーク系、ペアワイズランキング学習器 — です。「起きた」という二値シグナルを素の
評価回帰モデルに流し込むのは、問題の構造を無駄にします。

**評価指標**。ここが最も見落とされがちな要点です。明示的評価なら RMSE や MAE —
予測評価と実評価の平均誤差 — を報告するかもしれません。しかしその指標は暗黙的
データには *無意味* です。誤りを測るべき「真の評価」が存在しないからです。暗黙的
推薦は **上位 K 件のランキング** タスク — ユーザーが関わる可能性が最も高い数件を
提示する — なので、ランキング指標で評価します。**Recall@K**、**nDCG@K**、**MAP** です。
これらは「ユーザーが実際に相互作用したアイテムが、リストの上位に現れたか」を問います。
定義と数式は
[推薦の評価指標](/ja/learn/concepts/evaluation-metrics) を参照してください。

## Recotem は暗黙的フィードバックをどう扱うか

Recotem は暗黙的フィードバックを前提に一から作られています（暗黙的フィードバック
向けのレコメンダーライブラリ
[irspack](/ja/learn/concepts/recommendation-system) を基盤としています）。与えるのは
**相互作用の行** — (ユーザー, アイテム) のイベント 1 件につき 1 行 — で、各相互作用が
存在することを正のシグナルとして扱います。スキーマに評価やスコアの列はありません。
その相互作用が起きたという事実そのものがデータです。

最小構成の [CSV ソース](/ja/docs/data-sources/csv) と
[スキーマ](/ja/docs/recipe-reference#schema) は次のようになります。

```csv
user_id,item_id,timestamp
u-1001,item-8843,2026-05-01T09:12:00Z
u-1001,item-2290,2026-05-01T10:03:00Z
u-2087,item-8843,2026-05-02T18:40:00Z
```

```yaml
schema:
  user_column: user_id
  item_column: item_id
  time_column: timestamp   # 時系列での学習/評価分割にのみ使用
```

星評価を入れる場所がないことに注目してください — Recotem がそれをモデル化しない
からです。ソースに `rating` や `quantity` の列があっても単純に無視され、
[レシピ](/ja/docs/recipe-reference) はユーザー、アイテム、そして（任意で）時刻だけを
マッピングします。[`cleansing.dedup`](/ja/docs/recipe-reference#cleansing) の工程が
重複した (ユーザー, アイテム) ペアをまとめるため、相互作用行列は実質的に二値の
有無となり、これは暗黙的モデルが期待する形です。

Recotem が学習できるアルゴリズムはすべて、その暗黙的相互作用行列の上で動作します。

- **IALS** — 上で説明した信頼度重み付けのモデル、implicit alternating least
  squares。強力な汎用ベースラインです。
- **BPRFM** — Bayesian Personalized Ranking で学習する factorization machine。
  ネガティブサンプリング / ペアワイズ方式です。
- **RP3beta** — グラフのランダムウォーク系モデルで、「一緒に買われる/見られる」
  共起パターンで優れた結果を出します。
- **CosineKNN**、**DenseSLIM**、**TruncatedSVD** — アイテム類似度、疎な線形モデル、
  潜在因子モデルで、いずれも二値行列に直接フィットします。
- **TopPop** — 非パーソナライズの人気度ベースライン。探索に妥当な下限を与えます。

[`training.algorithms`](/ja/docs/recipe-reference#training) に複数を並べると、
Recotem の Optuna 探索が各アルゴリズムを試し、最良のものを残します。タスクが
ランキングであるため、[`metric`](/ja/docs/recipe-reference#training) フィールドは
`cutoff`（リスト長 K）とともに `ndcg`、`map`、`recall`、`hit` を受け付けます。これは
暗黙的データにとって意味のあるランキング指標そのものであり、RMSE のような評価誤差
指標ではありません。

::: tip 「ない」は「嫌い」ではない
Recotem のモデルがユーザーの未相互作用アイテムを返すとき、それは評価を予測して
いるのではなく、*推定された興味の順に候補をランク付け* しています。すでに保有して
いるアイテムを隠すには、[recommend エンドポイント](/ja/learn/use-cases/purchase-logs)
の `exclude_items` を使ってください。モデルがそれらを「消費済みと知っている」ことを
期待するのは適切ではありません。
:::
