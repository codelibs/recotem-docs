# 推薦の評価指標：nDCG・MAP・Recall@K

レコメンダーを本番投入する前に、あるモデルが別のモデルより優れているかを示す
「数値」が必要です。**nDCG**、**MAP**、**Recall@K** はその標準的な答えです。
これらは *ランキング* 指標であり、推薦リストの上位が、ユーザーが実際に求めていた
アイテムとどれだけ一致しているかを測ります。このページでは各指標を定義し、
小さな例を手計算で確認し、Recotem が `metric` と `cutoff` フィールドを使って
勝者モデルをどう選ぶのかを具体的に示します。

## なぜオフライン指標が必要か

レコメンダーの本当の評価基準はオンライン A/B テスト — 実際のユーザーと実際の
クリック — です。しかし、あらゆる候補モデルのあらゆるハイパーパラメータを A/B
テストすることはできません。時間もコストもかかり、ダメなランキングをユーザーに
見せるリスクもあります。そこでまず **オフライン評価** を行います。各ユーザーの
インタラクションの一部を取り置き（ホールドアウト）、残りで学習し、モデルに
アイテムをランク付けさせ、取り置いたアイテムが上位に戻ってくるかを確認します。
nDCG@20 のような単一のスカラー値があれば、自動探索が数分で何百ものモデルを
比較し、最良のものだけをオンラインテストに昇格させられます。

オフライン指標はあくまで *代理指標* であり、真実ではありません。ユーザーが
すでにインタラクションしたアイテムを当てることを報酬とするため、新しい
エンゲージメントを生むこととは必ずしも一致しません。高いオフラインスコアは
「必要条件だが十分条件ではない」と捉え、勝者は必ずオンラインで確認しましょう。

## 前提：関連アイテムと上位 K 件リスト

以下のすべての指標は、1 人のユーザーについて次の 2 つを比較します。

- **関連集合（relevant set）** — そのユーザーについて取り置いたアイテム（正解データ）。
- **上位 K 件リスト（top-K list）** — 学習データですでにインタラクション済みの
  アイテムを除外したうえで、モデルが最も高くランク付けした K 件。

取り置いたアイテムが上位 K 件リストに現れたら **ヒット（hit）** です。
レコメンダーはランク付きリストを返すため、ヒットが *どこに* 現れるかが重要です。
ランク 1 位の関連アイテムは、同じアイテムがランク 10 位にあるより価値があります。
この順序への感度こそが、優れたランキング指標と単純なヒット数を分けるものです。

`K` は **カットオフ（cutoff）** — 評価するリスト長です。Recotem ではこれを
`cutoff` と呼び、既定値は 20 です。

## Recall@K と Precision@K

最も単純な 2 つの指標はヒット数を数え、割る対象だけが異なります。

```text
Recall@K    = (上位 K 件に含まれる関連アイテム数) / (関連アイテムの総数)
Precision@K = (上位 K 件に含まれる関連アイテム数) / K
```

**Recall@K** は「ユーザーが求めた全アイテムのうち、K 枠でどれだけ拾えたか」を
表します。**Precision@K** は「見せた K 件のうち、求められていたものはいくつか」を
表します。どちらも上位 K 件 *内* の順序は考慮しません — ランク 1 位のヒットと
ランク K 位のヒットは同じ扱いです。いずれも 0 から 1 の範囲を取ります。

Precision と Recall はトレードオフの関係にあります。だからこそ、後述の平均適合率
（average precision）はリスト全体で両者を統合します。

## MAP — 平均適合率の平均

MAP はヒットを *早い順位に* 置くことを報酬とし、ヒットが起きた各順位で測った
Precision を平均します。1 人のユーザーについての **カットオフ K での平均適合率
（Average Precision at K）** は次のとおりです。

```text
AP@K = (1 / min(R, K)) * ( ランク k=1..K についての Precision@k * rel_k の総和 )

  rel_k = ランク k のアイテムが関連なら 1、そうでなければ 0
  R     = このユーザーの関連アイテム数
```

`rel_k` が非ヒットをゼロにするため、ヒットとなった順位だけが寄与し、各ヒットには
*その深さでの* Precision が与えられます。したがって早いヒットほどスコアを押し上げ
ます。**MAP** は、この `AP@K` を全テストユーザーで平均したものです。Recall や
Precision と同様、[0, 1] の範囲に収まります。

## nDCG@K — 割引利得に基づく指標

**nDCG**（normalized Discounted Cumulative Gain、正規化割引累積利得）は、最も
広く報告されるランキング指標であり、Recotem の既定値です。滑らかな対数割引を
適用し、リストの深い位置で見つかった関連性ほど価値が段階的に小さくなります。

まず **DCG@K** — 各アイテムの利得を順位割引で割った総和 — から始めます。

```text
DCG@K = ランク k=1..K についての ( rel_k / log2(k + 1) ) の総和
```

二値の関連性では `rel_k` は 0 か 1 です。割引 `log2(k+1)` は深さとともに増える
ため、ランク 1 は利得を丸ごと保ち（`log2(2) = 1`）、ランク 3 は半分に
（`log2(4) = 2`）……となります。DCG 単体は上限がなく、ユーザーの関連アイテム数に
依存するため、**理想 DCG（IDCG@K）** — すべての関連アイテムを最上位に並べた場合の
DCG — で正規化します。

```text
IDCG@K = ランク k=1..min(R, K) についての ( 1 / log2(k + 1) ) の総和

nDCG@K = DCG@K / IDCG@K
```

IDCG で割ることで、すべてのユーザーが共通の [0, 1] 軸に再スケールされ、1.0 が
完璧なランキングを意味します。このユーザーごとの正規化のおかげで、関連アイテム
数が大きく異なるユーザー間でも nDCG を比較できます。

## 計算例

**関連（取り置いた）アイテムが 3 件：A, B, C** のユーザーを考え、`K = 5` とします。
モデルが次のランク付きリストを返したとします（`X`, `Y`, `Z` は非関連アイテム）。

`[ A, X, B, Y, Z ]`

3 件の関連アイテムのうち 2 件がヒット（ランク 1 の A、ランク 3 の B）で、C は
一度も現れません。DCG の計算を順位ごとに示します。

| ランク k | アイテム | 関連？ | rel_k | 割引 1/log2(k+1) | 寄与 |
|--------|------|-------|-------|-------------------|------|
| 1 | A | あり | 1 | 1.000 | 1.000 |
| 2 | X | なし | 0 | 0.631 | 0.000 |
| 3 | B | あり | 1 | 0.500 | 0.500 |
| 4 | Y | なし | 0 | 0.431 | 0.000 |
| 5 | Z | なし | 0 | 0.387 | 0.000 |

`DCG@5 = 1.000 + 0.500 = 1.500` です。理想的なランキングでは A, B, C を上位 3 枠に
並べます。

`IDCG@5 = 1/log2(2) + 1/log2(3) + 1/log2(4) = 1.000 + 0.631 + 0.500 = 2.131`

このユーザーについての各指標は次のとおりです。

| 指標 | 計算 | 値 |
|--------|-------------|------|
| Recall@5 | 2 ヒット / 3 関連 | 0.667 |
| Precision@5 | 2 ヒット / 5 枠 | 0.400 |
| AP@5 | (1/3) × (Precision@1 + Precision@3) = (1/3) × (1.000 + 0.667) | 0.556 |
| nDCG@5 | 1.500 / 2.131 | 0.704 |

指標ごとに強調点が異なる点に注目してください。Precision は空いた 3 枠に引き下げ
られ、Recall は順序をまったく考慮せず、nDCG はランク 1 の早いヒットで報われつつ
C を取りこぼした分だけ罰せられ、その中間に落ち着きます。これらをすべてのテスト
ユーザーで平均すると、データセット全体のスコアになります。

## ランキング指標 vs 評価値（rating）指標

上記の指標は **ランキング指標** — 並べられたリストを評価します。別系統の
**評価値指標（rating metrics）** である RMSE や MAE は、予測された *スコア* を
評価します。

```text
RMSE = sqrt( mean( (予測評価値 - 実際の評価値)^2 ) )
```

評価値指標は、映画のスター評価を予測することが課題だった明示的フィードバックの
時代に由来します。数値の誤差を測る一方で、リストの順序をまったく無視します —
RMSE が優秀でも、上位に間違ったアイテムを並べるモデルはあり得ます。

現代のレコメンダー、そして Recotem は **ランク付きの上位 K 件リスト** を出力する
ため、ランキング指標が適切な道具です。シグナルが暗黙的（クリック、購買）でも
明示的（評価値）でも、最終的に配信するのは並び順であり、Recall@K・MAP・nDCG@K は
まさにそれを評価します。フィードバックの種類がパイプライン全体をどう左右するかは
[暗黙的・明示的フィードバック](/ja/learn/concepts/implicit-explicit-feedback) を
参照してください。

## 学習/評価データ分割とリークの注意点

オフラインの数値が信頼できるのは、それを生んだデータ分割が誠実な場合だけです。
次の落とし穴に注意してください。

- **時系列リーク。** ランダム分割では、ユーザーの *未来* のインタラクションが
  学習データに、*過去* が評価データに入ることがあり、モデルが実質的に答えを
  盗み見てしまいます。本番（過去から未来を予測）を模すには、時系列ベースの分割を
  使います。Recotem は `time_user`（各ユーザーの直近インタラクションを取り置く）と
  `time_global`（単一のグローバルな時刻カットオフ）を提供します。
  [レシピリファレンス](/ja/docs/recipe-reference#training) を参照してください。
- **既知アイテム。** 学習中にユーザーがインタラクションしたアイテムは、スコア
  計算の前に推薦リストから除外しなければなりません。さもないと「すでに持っている
  もの」を推薦したことで加点されてしまいます。Recotem の評価はこれを処理します。
- **人気バイアス。** グローバルに人気のアイテムを推薦すると、人気アイテムは定義上
  多くのユーザーのホールドアウト集合に含まれるため、見かけ上のスコアが高く出ます。
  探索には必ず人気ベースライン（Recotem の `TopPop`）を含め、より凝ったモデルが
  実際にどれだけ上回るかを確認しましょう。
- **評価集合でのチューニング。** ハイパーパラメータ探索が最大化するスコアは
  *検証* 推定値です。そのまさに同じ分割で最良に見えたモデルを選んでいるため、
  構造的に楽観的です。絶対値を信じる前に、ライブ A/B テストで勝者を確認して
  ください。

分割方式の選び方の実践は [レコメンダーを評価する](/ja/learn/how-to/evaluate) の
ハウツーで解説しています。

## Recotem での `metric` と `cutoff` の使い方

Recotem のレシピでは、評価は `training` ブロックの 2 つのフィールドで設定します。
`metric` は Optuna 探索が最大化するランキング指標を選び、`cutoff` はそれを測る K を
設定します。

```yaml
training:
  algorithms: [IALS, RP3beta, TopPop]
  metric: ndcg      # ndcg | map | recall | hit （既定値: ndcg）
  cutoff: 20        # 評価に使うリスト長 K（既定値: 20、1 以上）
  split:
    scheme: time_user
    heldout_ratio: 0.1
    seed: 42
```

`metric` フィールドは、次の 4 つの値のいずれかを受け付けます。

| `metric` | 最大化する対象 | 使いどころ |
|----------|-----------|----------|
| `ndcg` | nDCG@cutoff | 上位付近の順序品質を重視する場合 — 妥当な既定値。 |
| `map` | MAP@cutoff | 早いヒットを報酬にしたいが、平均適合率の枠組みを好む場合。 |
| `recall` | Recall@cutoff | 順序は問わず、K 枠に関連アイテムが現れるかだけを重視する場合。 |
| `hit` | Hit-rate@cutoff | ユーザーごとに上位 K 件へ関連アイテムが *1 件以上* 入れば十分な場合。 |

`recotem train` の実行中、Optuna は `algorithms` にわたって探索を行い、各トライアル
を選んだ `metric`（`cutoff` で測定）でホールドアウト分割に対し評価し、最高スコアの
モデルを残します。その勝者の値は、署名済みアーティファクトのヘッダに `best_score`
として（`metric` と `cutoff` とともに）書き込まれるため、ペイロードを読み込まずに
デプロイ済みモデルのスコアを確認できます。

```bash
recotem inspect artifacts/purchase_history.recotem
```

スコアは測定に用いた指標とカットオフとともに保存されるため、2 つのアーティファクト
を意味のある形で比較できるのは、両者が同じ `metric` と `cutoff` で学習された場合
だけです。全フィールドは
[レシピリファレンス](/ja/docs/recipe-reference#training) に記載しています。
