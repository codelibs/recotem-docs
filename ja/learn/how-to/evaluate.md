# レコメンドの評価方法（オフライン評価）

レコメンドモデルを本番に出す前に、はっきり答えておくべき問いがあります。
*このモデルは本当に良いのか？* **オフライン評価** は、テストしていない
モデルをユーザーにさらすことなくこの問いに答えます。学習時にモデルが一度も
見ていないインタラクションを取り置き、それをモデルに予測させ、レコメンド
リストがその取り置いたアイテムをどれだけ言い当てられるかを採点します。この
ページでは、分割戦略、スコアをこっそり水増しする落とし穴、ランキング指標の
読み方、そして Recotem が実際の `metric` / `cutoff` に対して
[Optuna](https://optuna.org/) 探索を実行し、勝ち残った `best_score` を報告する
仕組みを解説します。

指標そのものの定義や数式が知りたい場合は、先に
[レコメンド評価指標: nDCG, MAP, Recall@K](/ja/learn/concepts/evaluation-metrics)
を読んでください。このページはその実践編 — *どう* 評価を実行し、結果を読むか
に焦点を当てます。

## インタラクションを分割する: 学習・検証・テスト

オフライン評価はデータの分け方で成否が決まります。モデルは一方の切れ端で
学習し、まだ見ていないもう一方の切れ端で採点されます。よく使われる戦略は
3 つです。

### ランダムホールドアウト

各ユーザーのインタラクションから一定割合をランダムに取り置いて採点します。
最もシンプルなベースラインで、ユーザーあたりのテストシグナルを最大化できます
が、時間を無視します。あるインタラクションの *前* に起きた学習データで採点
される、といったことが起こり得ます。順序が問題にならない静的なカタログでは
これで十分で、Recotem のデフォルトでもあります（`split.scheme: random`）。

### Leave-one-out（1 件抜き出し）

ユーザーごとにちょうど 1 件 — 通常はそのユーザーの **最新** の 1 件 — を
取り置き、残りで学習します。「このユーザーが次に何をするか予測する」ことこそ、
本番でレコメンダーに問われる典型的な問いなので、leave-one-out は直感的で
文献でも広く使われます。難点はテストセットがユーザーあたり 1 件と極端に小さく
分散が大きいため、実行ごとにスコアが揺れやすいことです。

### 時系列（時間ベース）分割

ある 1 つのカットオフ時刻を選びます。それより **前** はすべて学習データ、
**以降** はすべてテストセットです。モデルは常に過去だけで学習し未来で採点
される — まさに本番でのデプロイのされ方 — ので、これは最も誠実な本番の
シミュレーションです。ランダム分割が隠してしまうコンセプトドリフトも表面化
します。代償として、直近にしか履歴のないユーザーは学習履歴を持たず
コールドスタートになり得ます。

::: tip Recotem の分割スキームと各戦略の対応
Recotem は `training.split.scheme` で 3 つのスキームを提供します。

- **`random`** — ユーザーごとにランダムに一様に取り置く（上記のランダム
  ホールドアウト）。`time_column` は使いません。
- **`time_user`** — 各ユーザーについて、そのユーザーのインタラクションのうち
  最新の `heldout_ratio` 分（`time_column` で並べ替え）を取り置きます。
  `heldout_ratio` を小さくすれば、leave-one-out の背後にある「ユーザーごとに
  最新を取り置く」という考え方になります。
- **`time_global`** — `time_column` の `1 - heldout_ratio` 分位点に単一の
  グローバルカットオフを置き、それ以降のインタラクションをすべて取り置きます。
  これが時系列分割です。

`time_user` と `time_global` は `schema.time_column` を必要とします。省略すると
レシピエラー（終了コード 2）になります。詳細なセマンティクスは
[レシピリファレンス](/ja/docs/recipe-reference#training) にあります。
:::

EC データやイベントデータ向けの時系列を意識した分割は、通常このようになります。

```yaml
schema:
  user_column: user_id
  item_column: item_id
  time_column: ts            # time_user / time_global に必須

training:
  algorithms: [IALS, RP3beta, TopPop]
  metric: ndcg
  cutoff: 20
  split:
    scheme: time_user        # random | time_global | time_user
    heldout_ratio: 0.1        # 取り置く割合、(0, 1) の範囲
    test_user_ratio: 1.0      # テスト分割に含めるユーザーの割合
    seed: 42
```

## よくある落とし穴

評価がモデルに有利なように仕組まれていれば、高いオフラインスコアには何の意味も
ありません。特にありがちな 2 つの失敗パターンは、専用の注意書きに値します。

### データリーク

**リーク**（leakage）とは、学習中にテストセットの情報がモデルに伝わってしまう
あらゆる経路のことです。オフラインでは素晴らしく見えるのに本番で崩れるスコアを
生みます。よくある原因は次のとおりです。

- **時系列リーク** — ランダム分割では、採点対象より *後* に起きた
  インタラクションでモデルが学習してしまうことがあります。未来を予測させたい
  レコメンダーなら、学習データが取り置きデータより厳密に前になるよう
  `time_user` か `time_global` で評価してください。
- **重複インタラクション** — 同じ（ユーザー, アイテム）ペアが学習とテストの
  両方にあると、タスクが自明に簡単になります。Recotem の
  [`cleansing.dedup`](/ja/docs/recipe-reference#cleansing)（デフォルト
  `keep_last`）が分割前に重複ペアをまとめます。
- **分割前の特徴量エンジニアリング** — 人気度・埋め込み・正規化統計量を
  *データセット全体*（テストを含む）で計算すると、集約シグナルがリークします。
  Recotem は分割を学習ドライバー内部で、どのモデルもデータを見る前に行うため、
  これを回避しています。

::: warning ランダム分割は時間を静かにリークさせる
`split.scheme: random` は手軽ですが時間順を守りません。本番のタスクが
「ユーザーが次に何をするか」を推薦するものであれば、ランダム分割は品質を
過大報告します。再現性が重要なあらゆる場面では、時系列スキーム
（`time_user` / `time_global`）を優先してください。
:::

### 人気バイアス

素朴な指標で良いスコアを取る最も簡単な方法は、最も人気のあるものを全員に
レコメンドすることです。人気アイテムは多くのユーザーの取り置きセットに現れる
ため、純粋な人気モデルはパーソナライズがゼロでも見かけ上まずまずの Recall@K を
稼いでしまいます。これに備えます。

- **探索に人気ベースラインを残す。** Recotem の `TopPop` レコメンダーは、
  まさに「最も人気のあるアイテムを推薦する」ものです。`training.algorithms` に
  含めておけば、毎回の実行が人気度の下限を報告します。パーソナライズ
  アルゴリズムが `TopPop` に勝てないなら、探索がそれを教えてくれます。
- **1 つの数字ではなく全体を読む。** nDCG で `TopPop` にわずかしか勝てない
  モデルは、デプロイの価値がないかもしれません。勝ち残った `best_score` を
  `TopPop` の試行と比較してください。
- **時系列分割を検討する。** 昨日のヒットが必ずしも明日のヒットではないため、
  人気の優位が小さくなります。

## 指標を読む: nDCG と Recall@K

ランキング指標は、上位 `K` 件のレコメンドをユーザーの取り置きセットと照合して
採点します。常時使う 2 つは次のとおりです。

- **Recall@K** — テストセットでユーザーが実際にインタラクションしたアイテムの
  うち、上位 `K` 件のレコメンドに現れる割合はどれくらいか？ *「関連アイテムを
  見つけられたか？」* に答え、リスト内の順序は無視します。範囲は `0`〜`1`、
  高いほど良い。
- **nDCG@K**（正規化割引累積利得）— Recall@K に似ていますが、関連アイテムを
  リストの **上位** に置くほど報酬が高く、対数的な位置割引を掛けたうえで理想的な
  並びで正規化します。*「関連アイテムを見つけ、**かつ** 適切に順位付けできたか？」*
  に答えます。範囲は `0`〜`1`、高いほど良い。

リスト内の位置があまり重要でないとき（大量の候補グリッド）は Recall@K を、
上位の枠がほとんどの価値を担うとき（最初のアイテムがクリックを集める短い
「あなたへのおすすめ」枠）は nDCG@K を使います。`K` は評価に使う `cutoff` で、
UI が実際に表示するリストの長さに設定してください。完全な定義、DCG/IDCG の
数式、具体例は
[レコメンド評価指標](/ja/learn/concepts/evaluation-metrics) にあります。

## Recotem の評価の仕組み: メトリクスに対する Optuna 探索

分割・採点・モデル比較を手作業で行う必要はありません。Recotem の学習
ドライバーがすべてを担い、その挙動は
[レシピ](/ja/docs/recipe-reference#training) の `training` ブロックだけで
決まります。

1. **分割。** クレンジング済みのインタラクションを `split.scheme` /
   `heldout_ratio` に従って、学習部分と取り置いた検証部分に分けます。
2. **探索。** `algorithms` の各アルゴリズムについて、Optuna が
   ハイパーパラメータを（各 irspack レコメンダーの組み込み範囲から）
   サンプリングし、合計 `n_trials` の試行を実行して、予算をアルゴリズム間で
   分け合います。
3. **採点。** 各試行は学習部分で学習し、取り置いた部分をあなたが選んだ
   `metric` と `cutoff` で評価します。例えば `metric: ndcg`、`cutoff: 20` なら
   nDCG@20 を計算します。
4. **選択。** 指標が最も高い試行が勝ちます。そのアルゴリズムが `best_class`、
   ハイパーパラメータが `best_params`、検証スコアが `best_score` になります。
   Recotem はその構成を全データで再学習し、署名済みアーティファクトを
   書き出します。

評価品質に効いてくるノブは次のとおりです。

| フィールド | 評価における役割 |
|-----------|-----------------|
| `metric` | 最適化するスコア: `ndcg` / `map` / `recall` / `hit`。デフォルト `ndcg`。 |
| `cutoff` | Recall@K / nDCG@K の `K` — 評価するリストの長さ。デフォルト `20`。 |
| `algorithms` | 候補モデル。人気度の下限として `TopPop` をリストに残す。 |
| `n_trials` | Optuna の総試行予算 — 多いほどハイパーパラメータを丁寧に探索する。 |
| `split.scheme` | `random` / `time_user` / `time_global` — 上記の落とし穴を参照。 |
| `split.heldout_ratio` | 採点用に取り置くインタラクションの割合。 |

探索は `best_class`・`best_score`・`n_completed` を含む `search_done` 構造化ログ
イベントを発行し、最終的な `train_done` イベントも `best_score` を再掲します。
どちらも [学習実行の監視](/ja/docs/operations#training-pipeline-events) に役立ちます。

::: warning 「全試行のスコアが 0.0」
完了したすべての試行がちょうど `0.0` になると、`recotem train` は
`code: zero_score` で終了コード 4 になります。これは通常、分割によって検証
セットが空または空同然になったことを意味します — ユーザーやインタラクションが
少なすぎる、あるいは利用可能なアイテム数より `cutoff` が大きい、などです。
`split.scheme: random` を試す、`split.heldout_ratio` を下げる、`cutoff` を
小さくするなどしてください。
[トラブルシューティング](/ja/docs/operations#recotem-train-exits-4-with-zero-score)
を参照してください。
:::

## アーティファクトヘッダーから `best_score` を読む

すべてのアーティファクトは評価結果を（HMAC 署名済みの）ヘッダーに記録するため、
デシリアライズや再学習をせずに、出荷済みモデルのスコアを読めます。
`recotem inspect` はヘッダーを検証して出力します。

```bash
recotem inspect ./artifacts/purchase_history.recotem
```

```text
HMAC: OK  (kid=prod-2026-q3)
{
  "recipe_name": "purchase_history",
  "best_class": "IALSRecommender",
  "best_score": 0.1873,
  "metric": "ndcg",
  "cutoff": 20,
  "data_stats": {"n_rows": 128443, "n_users": 5120, "n_items": 3311},
  "trained_at": "2026-07-08T09:14:52Z",
  "recotem_version": "2.0.0"
}
```

`best_score` は必ず `metric` と `cutoff` と **一緒に** 読んでください。裸の
`0.1873` は、それが nDCG@20 だと分からなければ無意味です。ヘッダーには
`best_params`（勝ち残ったハイパーパラメータ）と `data_stats`（行数・ユーザー
数・アイテム数）も含まれるので、2 つの学習実行の比較、再学習でスコアが向上した
かの確認、どのアルゴリズムが勝ったかの監査を、署名済みヘッダーだけで行えます。
同じ値は実行時に、認証付きの `/v1/health/details` エンドポイントでも公開されます。
`recotem inspect` は、HMAC とサイズのチェックがペイロードに触れる前に実行される
ため、信頼できないファイルや破損ファイルに対しても安全です。
[Operations Runbook](/ja/docs/operations#recotem-inspect-flags) を参照してください。

::: tip オフラインスコアは判決ではなくシグナル
オフラインの `best_score` が高いことは必要条件ですが十分条件ではありません。
指標は人気によってゲームできますし、オフラインデータは新規性・多様性・
レコメンドされたときのユーザーの反応を捉えられません。オフライン評価は、
*どの* モデルをオンライン A/B テストに掛ける価値があるかを決めるゲートとして
扱い、最終判断とは見なさないでください。
:::
